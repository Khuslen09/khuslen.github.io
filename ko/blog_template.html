01 — 개념

클라우드 컴퓨팅이란 무엇인가

NIST(미국 국립표준기술연구소)는 클라우드 컴퓨팅을 공유 풀에 접근하여 컴퓨팅 자원을 필요할 때 사용하고 반납하는 모델로 정의합니다. 이 정의에서 핵심은 두 가지입니다. "온디맨드(on-demand)"와 "사용량 기반 과금(pay-as-you-go)".

과거에는 서버를 구매하고, 설치하고, 유지하는 데만 수개월이 소요됐습니다. 클라우드는 이 사이클을 분(分) 단위로 압축했습니다. 인프라가 비즈니스 속도에 맞춰 움직이는 시대가 된 것입니다.

핵심 전환: 자본지출(CapEx) → 운영지출(OpEx). 자산을 소유하는 대신 서비스를 구독하는 방식으로 IT 경제학이 바뀌었습니다.
⚡

온디맨드 셀프서비스

사람의 개입 없이 필요할 때 즉시 자원을 프로비저닝

🌐

광범위한 네트워크 접근

인터넷을 통해 어디서든 접근 가능한 표준 메커니즘

📦

리소스 풀링

다중 고객에게 자원을 공유 제공하는 멀티테넌트 모델

핵심 포인트

클라우드의 5대 특성 (NIST): 온디맨드 셀프서비스, 광범위한 네트워크 접근, 리소스 풀링, 신속한 탄력성, 측정 가능한 서비스. 이 다섯 가지를 모두 만족해야 클라우드라고 부를 수 있습니다.

02 — 비교

온프레미스 vs 클라우드

"무조건 클라우드"라는 주장은 틀렸습니다. 두 환경은 트레이드오프 관계이며, 데이터 민감도·초기 투자 여력·내부 인력 수준에 따라 선택이 달라집니다.

온프레미스 (On-Premise)
서버 소유기업 직접 구축
초기 비용높음 (CapEx)
유지보수내부 IT 인력
확장성하드웨어 증설, 느림
가용성수동 이중화 필요
보안 정책자체 구축 가능
클라우드 (Cloud)
서버 소유공급자 제공·관리
초기 비용낮음 (OpEx)
유지보수공급자 담당
확장성자동 확장, 빠름
가용성다중 AZ 고가용성
보안 정책책임 공유 모델
주의: 온프레미스가 유리한 상황도 존재합니다. 극도로 민감한 데이터를 다루거나, 초기 투자 여력이 충분하고, 자체 IT 인력을 보유한 경우입니다.

03 — AWS

AWS는 어떻게 탄생했나

아마존은 원래 물류 회사입니다. 하지만 내부 IT 인프라가 너무 복잡해지면서 "이걸 표준화하지 않으면 성장 속도가 꺾인다"는 판단을 내립니다. 2002년 제프 베조스가 사내에 보낸 메일이 이 전환점입니다.

베조스 메일의 핵심: 모든 팀은 서비스 인터페이스로만 통신하라. 그리고 그 인터페이스는 처음부터 외부 개발자도 쓸 수 있도록 설계하라. 이 원칙이 AWS의 DNA가 됩니다.

2006년, 아마존은 EC2와 S3를 시작으로 상업용 퍼블릭 클라우드를 출시합니다.

AWS CLI — EC2 인스턴스 시작 
# EC2 인스턴스 생성 예시
aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type t3.micro \
  --key-name MyKeyPair \
  --security-group-ids sg-903004f8 \
  --subnet-id subnet-6e7f829e
영역 대표 서비스 분류 역할 요약
컴퓨팅 EC2, Lambda, EKS Compute 가상 서버 또는 서버리스 실행
스토리지 S3, EBS, EFS Storage 객체 / 블록 스토리지
데이터베이스 RDS, DynamoDB, Aurora Database 관계형 / NoSQL 관리형 DB
네트워킹 VPC, CloudFront, ELB Network 가상 네트워크, CDN, 로드밸런서
보안 IAM, WAF, GuardDuty Security 접근 권한, 위협 탐지, 암호화

04 — 인프라

AWS 글로벌 인프라 구조

AWS의 물리적 인프라는 세 계층으로 구성됩니다. 리전(Region) → 가용 영역(AZ) → 엣지 로케이션(Edge Location). 이 구조를 이해하지 않으면 고가용성 설계가 불가능합니다.

🌍

리전 (Region)

지리적으로 분리된 데이터센터 클러스터. 서울(ap-northeast-2), 버지니아(us-east-1) 등 수십 개 존재.

⚡

가용 영역 (AZ)

리전 내 물리적으로 분리된 데이터센터 그룹. 각 리전은 최소 3개 AZ로 구성됩니다.

🔗

엣지 로케이션

CloudFront CDN 캐싱을 위한 엣지 노드. 사용자와 가장 가까운 지점에서 콘텐츠를 서빙합니다.

실무 포인트: 고가용성(HA) 아키텍처의 기본은 멀티-AZ 배포입니다. 동일 리전 내 서로 다른 AZ에 애플리케이션을 분산해야 단일 장애 지점(SPOF)을 제거할 수 있습니다.

05 — 의사결정

리전 선택 — 기술·법률·비용의 트리플 레이어

리전 선택은 단순히 "가까운 곳"을 고르는 문제가 아닙니다. 기술(지연), 규제(데이터 주권), 비용(리전별 요금 차이) 세 축을 동시에 고려해야 합니다.

⏱
지연 시간 (Latency)
한국 사용자 대상 서비스라면 서울 리전(ap-northeast-2)이 기본값. 사용자와 서버 간 물리적 거리가 RTT(왕복 지연)에 직접 영향을 미칩니다.
🔧
서비스 가용성 (Supported Services)
신규 서비스는 특정 리전에서 먼저 출시됩니다. AI 서비스(Amazon Bedrock 등)는 북미·유럽 리전 중심으로 먼저 제공되는 경우가 많습니다.
💰
비용 (Cost)
동일 스펙의 EC2 인스턴스라도 리전별 요금 차이가 존재합니다. 서울 리전은 일반적으로 오하이오보다 약간 높습니다.
⚖️
법률 및 데이터 주권 (Compliance)
금융권은 전자금융감독규정에 따라 중요 정보의 국내 저장이 원칙이며, 해외 리전 사용 시 금감원 사전 승인이 필요합니다.

마무리

클라우드는 철학의 변화입니다

클라우드는 기술 선택지가 아닌 운영 철학의 변화입니다. 온프레미스가 "소유"를 전제로 한다면, 클라우드는 "사용"을 전제로 합니다. AWS는 이 철학을 가장 넓은 생태계 위에서 구현한 플랫폼입니다. 다음 포스팅에서는 VPC와 네트워크 보안 그룹 설계를 구체적으로 다뤄보겠습니다.
