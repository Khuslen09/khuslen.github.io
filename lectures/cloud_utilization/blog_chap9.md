## 1. 아키텍처란 무엇인가?

### 1.1 아키텍처의 정의

**아키텍처(Architecture)**는 시스템을 구성하는 컴포넌트와 그들 간의 관계, 배치, 흐름을 정의하는 **설계도**다.

- 서버, 데이터베이스, 스토리지, 네트워크, 보안 등의 구성요소가 서로 어떤 방식으로 연계되어야 하는지를 정의
- IT에서의 아키텍처는 인프라 구조, 데이터 흐름, 트래픽 처리 방식 등 **전체 시스템 동작 방식을 설계**하는 것

### 1.2 아키텍처가 중요한 이유

- 건축 설계도에 비유 가능: 튼튼하고 효율적인 구조를 만들기 위한 설계
- **아키텍처를 모르고 구축된 시스템은 유지보수 비용과 장애 위험이 증가**한다

---

## 2. 좋은 아키텍처의 6가지 요건

**AWS Well-Architected Framework**는 클라우드 환경에서 안정적이고 효율적인 시스템 설계를 돕기 위한 **설계 기준 가이드라인**이다. AWS에서 수천 개 고객 아키텍처를 분석한 경험을 바탕으로 만들어진 단순한 기술 기준이 아닌, **비즈니스 성공을 위한 설계 철학**이다.

### 6가지 핵심 품질(Pillar) 요약

| 요소 | 설명 |
|------|------|
| 운영 우수성 (Operational Excellence) | 모니터링 및 자동화 용이성 |
| 보안성 (Security) | 데이터 보호 및 접근 제어 |
| 신뢰성 (Reliability) | 장애가 발생해도 복구 가능 |
| 성능 효율성 (Performance Efficiency) | 자원 낭비 없이 빠른 처리 |
| 비용 최적화 (Cost Optimization) | 필요한 만큼만 자원을 사용 |
| 지속 가능성 (Sustainability) | 클라우드 워크로드 운영 시 환경적 영향을 최소화하는 능력 |

---

### 2.1 운영 우수성 (Operational Excellence)

**정의:** 시스템과 서비스를 안정적이고 효율적으로 운영하면서, 동시에 비즈니스 요구와 환경 변화에 맞춰 지속적으로 개선할 수 있는 능력. 운영팀이 단순히 장애를 "복구"하는 데 그치지 않고, **운영 과정 자체를 학습하고 개선하는 것**이 핵심.

#### 주요 원칙

**문서화와 표준화:**
- 운영 매뉴얼, Runbook, Playbook을 통해 일관된 절차 확보
- 사람이 매번 직접 판단하지 않도록 자동화 가능한 부분은 자동화

**관찰 가능성 (Observability):**
- 단순 모니터링(시스템 지표 수집)을 넘어 확장된 관측(로그, 메트릭, 트레이스)
- 문제 발생 시 "왜?"를 빠르게 추적할 수 있도록 데이터 기반 설계

**자동화된 운영:**
- 반복 작업(배포, 테스트, 알림)은 자동화하여 오류 최소화
- 사람이 개입하는 순간 오류 확률이 증가하므로 운영 절차를 코드화

**점진적 개선:**
- 큰 변화보다는 **작은 변경을 자주 적용** → 위험 분산
- 피드백 루프(Feedback Loop)를 통해 개선 사항을 운영에 반영

**비즈니스 목표 정렬:**
- 단순히 "서비스를 운영"하는 것이 아니라, 운영 지표가 비즈니스 KPI와 연계
- 예: 응답 시간 → 고객 이탈률, 가용성 → 매출 손실 방지

#### 대표적인 운영 우수성 지표

| 지표 | 설명 |
|------|------|
| 변경 실패율 (Change Failure Rate) | 배포 후 장애로 이어진 비율 |
| 평균 복구 시간 (MTTR) | 장애 복구 소요 시간 |
| 배포 빈도 (Deployment Frequency) | 얼마나 자주 변경을 반영하는가 |
| 평균 탐지 시간 (MTTD) | 장애를 얼마나 빨리 발견하는가 |

> 운영 우수성은 "운영을 단순 유지가 아닌 학습·개선·혁신의 과정"으로 보는 관점. 장애를 줄이는 것만이 아니라 변화에 강하고, 지속적으로 진화하는 운영 체계를 만드는 것이 목표.

---

### 2.2 보안 (Security)

**정의:** 시스템, 데이터, 애플리케이션을 무단 접근·변조·파괴로부터 보호하는 능력. 단순히 외부 침입만 막는 것이 아니라, **데이터 무결성 보장, 사용자 신뢰 확보, 법적·규제 준수**까지 포함.

#### 주요 원칙

**최소 권한 원칙 (Principle of Least Privilege):**
- 사용자·프로세스·서비스는 반드시 필요한 최소한의 권한만 가짐
- 기본은 "거부(Deny all) → 필요 시 허용(Allow specific)"

**방어 심층 (Defense in Depth):**
- 보안은 단일 계층이 아닌 **다중 계층 방어**

**데이터 보호:**
- 저장 시 암호화 (At-rest encryption), 전송 시 암호화 (In-transit encryption)
- 키/비밀번호는 안전하게 관리 (비밀 관리, 자동 회전)

**식별과 접근 제어 (Identity & Access Management):**
- 사용자·시스템의 정체성을 정확히 확인 (인증)
- 권한을 정책적으로 제어 (인가)

**보안 관찰 가능성 (Security Observability):**
- 로그·모니터링을 통해 비정상 행동 탐지
- 침입 탐지, 이상 행위 알림, 포렌식 기반 확보

**규정 준수 및 거버넌스:**
- 산업별 규제(금융, 의료, 개인정보법 등) 준수
- 정책 기반으로 보안 수준 일관성 유지

#### 대표적인 보안 지표

| 지표 구분 | 지표 내용 |
|---------|---------|
| 계정 보안 | MFA 적용률, 비밀번호/키 만료 정책 준수율 |
| 네트워크 | 차단된 공격 수, 비정상 트래픽 탐지율 |
| 애플리케이션 | 취약점 발견 건수, 패치 적용 소요 시간 |
| 데이터 | 암호화 적용률, 데이터 접근 로그 미검출률 |
| 운영 | 보안 사고 탐지 시간(MTTD), 대응 완료 시간(MTTR) |

> 보안은 단순히 시스템을 "닫아두는 것"이 아니라, 식별과 접근 관리 + 데이터 보호 + 관찰 가능성 + 규정 준수를 통해 위협을 예방·탐지·대응·복구하는 전 과정을 체계적으로 운영하는 것이 핵심.

### 2.3 신뢰성 (Reliability)

**정의:** 시스템이 장애나 예상치 못한 상황에서도 지속적으로 올바르게 동작하고, 빠르게 복구할 수 있는 능력. "서비스 중단을 최소화하고, 실패가 발생해도 자동으로 회복할 수 있는 시스템"이 목표.

**핵심 초점:** 내결함성(Fault Tolerance), 복원력(Resilience), 가용성(Availability)

신뢰성은 장애를 "피하는 것"이 아니라, **"장애를 견디고 빠르게 회복"**하는 능력. 장애가 발생할 수 있다는 전제를 바탕으로 자동 복구, 중복성, 데이터 보호, 지속적 개선을 통해 시스템을 더 강하게 만드는 것이 핵심.

#### 주요 원칙

**장애는 피할 수 없음을 전제로 설계:**
- 하드웨어 고장, 네트워크 지연, 소프트웨어 버그는 필연적
- "장애가 없다(no failure)"가 아니라, "장애에도 지속적으로 운영된다(no outage)"를 목표

**자동 복구 (Automatic Recovery):**
- 장애 감지 후, 사람이 개입하기 전 시스템이 스스로 회복
- 예: 헬스 체크 실패 시 자동 재시작, 장애 서버 자동 교체

**중복(Redundancy)과 분산(Distribution):**
- 단일 장애 지점(SPOF, Single Point of Failure) 제거
- 멀티 노드, 멀티 존, 멀티 리전 등 물리적/논리적 중복 설계

**확장성(Scalability) 보장:**
- 시스템이 부하 증가에도 안정적으로 동작
- 수직 확장(Scale Up)보다 **수평 확장(Scale Out)** 중심

**장애 대비 훈련과 시뮬레이션:**
- 카오스 엔지니어링(Chaos Engineering)
- 장애 발생을 가정하고 대응 시나리오 검증

#### 대표적인 신뢰성 지표

| 지표 | 설명 |
|------|------|
| 가용성 (Availability) | 시스템이 정상 동작하는 시간 비율. 예: 99.9%(연간 8시간 45분 다운) / 99.99%(연간 52분 다운) |
| MTBF (Mean Time Between Failures) | 평균 장애 간격 |
| MTTR (Mean Time To Recovery) | 평균 복구 소요 시간 |
| RPO/RTO 달성률 | 복구 전략이 SLA를 충족하는지 여부 |
| 오류율 (Error Rate) | 요청 대비 실패 응답 비율 |

### 2.4 성능 효율성 (Performance Efficiency)

**정의:** 적절한 컴퓨팅 자원과 아키텍처를 활용하여 워크로드 요구사항을 효율적으로 충족하는 능력. 같은 비용·리소스로 더 많은 성능을 내고, 수요 변화에도 안정적인 응답 성능을 유지하는 것.

> "적은 자원으로 더 많은 성능을 내면서도, 수요 변화에 탄력적으로 대응하는 아키텍처를 설계하는 것"

#### 주요 원칙

**자원 최적화 (Resource Optimization):**
- 워크로드 특성(읽기/쓰기 비율, 배치/실시간, 동시성)에 맞게 자원 선택
- CPU, 메모리, 스토리지, 네트워크의 균형 유지

**탄력적 확장성 (Elastic Scalability):**
- 부하 증가·감소에 맞춰 자원을 자동으로 조정
- Scale-out(수평 확장) 선호, 필요 시 Scale-up 보완

**지속적 혁신 (Continuous Improvement):**
- 최신 기술(서버리스, 컨테이너, 신형 하드웨어, 캐싱) 적극 활용
- 아키텍처는 시간이 지남에 따라 리팩토링/최적화

**데이터 기반 의사결정:**
- 성능 측정·분석에 기반해 자원 크기 조정
- 추측이 아니라 실측 지표 기반 최적화

**아키텍처 적합성 (Workload Fit):**
- 정형 데이터는 관계형 DB, 초저지연 대규모 처리에는 NoSQL 등 워크로드 맞춤형 기술 선택

#### 대표적인 성능 효율성 지표

| 지표 | 설명 |
|------|------|
| 응답 시간 (Response Time) | 요청에서 응답까지 걸리는 시간 |
| 처리량 (Throughput) | 초당 요청 수(RPS), 초당 트랜잭션 수(TPS) |
| 자원 활용률 (Utilization) | CPU, 메모리, 네트워크, IOPS |
| 확장성 지표 | 부하 증가 시 성능 선형 확장 여부 |
| 비용 효율성 | 단위 비용당 처리량 (Cost per RPS, Cost per Transaction) |

### 2.5 비용 최적화 (Cost Optimization)

**정의:** 필요한 성능과 가용성을 확보하면서도 최소 비용으로 리소스를 운영하는 능력. 핵심은 "성능 저하 없는 비용 절감"이며, 단순 절약이 아니라 **효율적인 투자를 통해 ROI(투자 대비 효과)를 극대화**하는 데 목적이 있다.

비용 최적화는 단순히 절약이 아니라, **성능·신뢰성을 유지하면서 낭비 없는 아키텍처를 설계하는 것**.

#### 주요 원칙

**가시성 (Visibility):**
- 모든 비용은 추적 가능해야 함
- 서비스·부서·팀별 비용 태깅 및 모니터링

**적절한 자원 선택 (Right Sizing):**
- 워크로드에 맞는 자원 크기와 유형을 선택
- 오버 프로비저닝(과잉 할당) 방지, 언더 프로비저닝(성능 저하) 방지

**탄력적 사용 (Elastic Usage):**
- 수요 변화에 맞춰 자동 확장/축소
- 유휴 자원 제거, 스케줄링을 통한 사용 최적화

**수명 주기 관리 (Lifecycle Management):**
- 데이터·스토리지·애플리케이션의 사용 주기에 맞게 비용 효율적 계층 사용
- 불필요한 로그·백업 자동 삭제/아카이빙

#### 대표적인 비용 최적화 지표

| 지표 | 설명 |
|------|------|
| 서비스별 비용 분포 | Compute / Storage / Network / DB 비율 |
| Idle 자원 비율 | 사용량 5% 이하 자원의 비중 |
| Cost per Transaction / per Request | 요청 1건당 비용 |
| 예산 대비 실제 비용 | Budget vs Actual |

---

### 2.6 지속 가능성 (Sustainability)

**정의:** IT 인프라와 애플리케이션이 환경적 영향을 최소화하면서도 장기간 안정적으로 운영될 수 있는 능력. 에너지 효율 최적화 + 탄소 배출 최소화 + 장기적 운영 안정성을 동시에 고려하는 아키텍처 설계 원칙.

지속 가능성은 단순한 환경 보호 차원을 넘어, **낭비 없는 자원 활용 + 에너지 효율적 아키텍처 + 장기 운영 가능성을 확보**하는 것이 목표. 성능·비용·보안과 같은 기술적 품질뿐 아니라 **환경적 책임까지 고려하는 현대적 아키텍처 설계 원칙**.

#### 주요 원칙

**효율적인 자원 활용:**
- 과잉 프로비저닝 방지, 필요한 만큼만 사용
- 사용하지 않는 리소스는 즉시 해제

**에너지 효율성 극대화:**
- 고효율 하드웨어, 최신 CPU/GPU, 최적화된 네트워크·스토리지 사용
- 워크로드를 에너지 효율이 높은 데이터센터/리전으로 배치

**수요 기반 탄력 운영:**
- 유휴 자원 최소화 → 필요할 때만 리소스 활성화
- 배치 작업은 에너지 효율이 높은 시간대에 실행

**소프트웨어 최적화:**
- 불필요한 연산 제거, 효율적 알고리즘 선택
- 데이터 전송·저장을 줄이는 방식으로 애플리케이션 설계

## 3. AWS 아키텍처의 기초 요소

### 3.1 클라우드 네이티브 아키텍처 (Cloud-Native Architecture)

단순히 "클라우드에서 돌아가는 시스템"을 뜻하는 게 아니라, **클라우드 환경의 특성과 장점을 최대한 활용하여 설계한 아키텍처**를 의미.

- **구성:** 컨테이너, 오케스트레이션(Kubernetes), CI/CD, 서버리스 기반
- **장점:** 자동 확장, 글로벌 서비스 제공에 최적화
- **예시:** AWS Lambda 기반 서버리스 웹앱, SaaS 서비스

### 3.2 AWS 아키텍처 기본 구성 요소

| 요소 | 설명 | 예시 |
|------|------|------|
| 컴퓨팅 | 애플리케이션 실행 | EC2, Lambda |
| 스토리지 | 데이터 저장 | S3, EBS, EFS |
| 네트워크 | 자원 연결 및 트래픽 분산 | VPC, Load Balancer, Route 53 |
| 데이터베이스 | 구조화된 데이터 저장 | RDS, DynamoDB |
| 보안 | 접근 제어 및 데이터 보호 | IAM, WAF, GuardDuty |
| 모니터링 & 로깅 | 시스템 상태 추적 | CloudWatch, CloudTrail |

### 3.3 EC2 인스턴스 아키텍처 특징

**비용 효율성:**
- 다양한 과금 모델 제공
- 다양한 스토리지 옵션

**스토리지:**
- 인스턴스 스토어(임시 저장소)와 EBS(Elastic Block Store, 영구 저장소)를 지원
- S3, EFS 등 다른 AWS 스토리지 서비스와도 연계 가능

**네트워킹/보안:**
- VPC 내에서 실행되어 보안 그룹(Security Group), 네트워크 ACL로 접근 제어 가능

### 3.4 RDS 인스턴스 아키텍처 특징

**확장성:**
- 수직 확장(더 큰 인스턴스 타입 선택) 가능
- 수평 확장(읽기 전용 복제본 추가)으로 읽기 처리량 확장

## 4. 간단한 웹 아키텍처 예시

### 4.1 3-Tier 웹 아키텍처 구성

전형적인 AWS 기반 웹 서비스는 다음과 같은 3계층 구조로 설계한다:

```
[사용자] → [Web Server (EC2 - Public Subnet)]
         → [App Server (EC2 - Private Subnet)]
         → [Amazon RDS (Private Subnet)]
         ↕
       [S3 Bucket] (정적 리소스 저장)
```

**각 계층 설명:**

| 계층 | 서비스 | 역할 | 서브넷 |
|-----|--------|------|--------|
| 프론트엔드 (Web Tier) | EC2 (Web Server) | HTML/CSS/JS 등 정적 콘텐츠 제공, 사용자 요청 수신 | Public Subnet |
| 백엔드 (App Tier) | EC2 (App Server) | 비즈니스 로직 처리, API 응답 | Private Subnet |
| 데이터 계층 (DB Tier) | Amazon RDS | 관계형 데이터 저장 및 조회 | Private Subnet |
| 정적 스토리지 | S3 Bucket | 이미지, 동영상, 파일 등 정적 리소스 저장 | VPC 외부 (관리형) |

### 4.2 예시 아키텍처 주요 특징

- **S3**는 정적 리소스를 빠르게 제공 → 설정에 따라 S3의 정적 웹 호스팅 기능만으로도 간단한 정적 웹사이트 가능
- **실무 팁:**
  - EC2와 S3 간 연동 시 **IAM 역할**을 통해 접근 권한 부여 필요
  - RDS와 EC2 인스턴스는 **멀티 AZ(가용영역)에 이중화**를 통해 가용성 확보 가능

## 5. VPC 안에서 서비스가 연결되는 구조

### 5.1 VPC 네트워크 구조 설계

실습 기준 VPC 설계 예시:

```
AWS Cloud
└── Region: ap-northeast-2 (서울)
    └── VPC: 10.10.0.0/16
        ├── Availability Zone - a
        │   ├── Public Subnet 1:  10.10.20.0/24  (Web Server EC2)
        │   ├── Private Subnet 1: 10.10.21.0/24  (App Server EC2)
        │   └── Private Subnet 2: 10.10.22.0/24  (Amazon RDS)
        └── Internet Gateway (외부 인터넷 연결)
```

### 5.2 서브넷 역할 구분

| 서브넷 유형 | 특징 | 배치 서비스 |
|---------|------|---------|
| **Public Subnet** | Internet Gateway를 통해 외부 인터넷 접근 가능 | Web Server, Load Balancer, NAT Gateway |
| **Private Subnet** | 외부 인터넷 직접 접근 불가. 내부 통신만 허용 | App Server, DB (RDS), 내부 서비스 |

### 5.3 연결 흐름 보안 요소

VPC 내 서비스 연결 시 설정이 필요한 보안 요소:

- **EC2 인바운드 규칙:** 80/443 포트 오픈 (웹 트래픽 허용)
- **S3:** 퍼블릭 비활성화 권장, EC2 IAM 역할로 접근
- **라우팅 테이블:** Internet Gateway(IGW) 경로가 추가되어야 외부 통신 가능
- **NACL (Network Access Control List):** 서브넷 단위로 접근 통제 가능

### 5.4 트래픽 흐름 요약

```
사용자 → Internet Gateway → Web Server (Public Subnet)
                           → App Server (Private Subnet)
                           → RDS (Private Subnet)
웹서버 → S3 Bucket (정적 콘텐츠)
```

## 6. 아키텍처 다이어그램 그리기

### 6.1 다이어그램 구성 단계

**Step 1 — 네트워크 환경 표현:**
- 리전(ap-northeast-2), AZ(가용영역), VPC, Subnet, Internet Gateway 등 네트워크 계층 표시

**Step 2 — 구성 요소 배치:**
- 사용자(Users), EC2 인스턴스 웹/앱 서버, S3, RDS를 각각 해당 네트워크 환경에 배치

**Step 3 — 요청 흐름 화살표 표현:**
- 정적 콘텐츠 요청: 사용자 → IGW → Web Server → S3
- 동적 콘텐츠 요청: 사용자 → IGW → Web Server → App Server → RDS

### 6.2 최종 아키텍처 다이어그램 구조

```
[Users]
   |
   ↓
[Internet Gateway]
   |
   ↓
[VPC 10.10.0.0/16]
   |
   ├── Public Subnet 10.10.20.0/24
   │       └── EC2 Instance (Web Server) ←→ [S3 Bucket]
   |
   ├── Private Subnet 10.10.21.0/24
   │       └── EC2 Instance (App Server)
   |
   └── Private Subnet 10.10.22.0/24
           └── Amazon RDS
```

## 7. AWS Well-Architected Framework 심화

### 7.1 Well-Architected Framework 목적

- 시스템 설계자가 스스로 **"내 시스템은 잘 설계되었는가?"**를 검토할 수 있도록 시스템을 평가하고 개선할 수 있도록 설계 기준 제공
- 클라우드 시스템이 보안, 비용, 성능, 운영, 복원력 등 측면에서 최적화되어 있는지를 점검
- **높은 가용성과 보안, 비용 효율성**을 갖춘 시스템 구축 지원

### 7.2 Well-Architected Framework 구성

- **6가지 설계 원칙(Pillar)**로 구성: 보안, 신뢰성, 성능 효율성, 비용 최적화, 지속 가능성, 운영 우수성
- 각 원칙마다 **핵심 질문(Key Questions)**과 **모범 사례(Best Practices)** 제공

### 7.3 6대 원칙별 핵심 질문 및 실무 적용

#### 보안(Security) — 핵심 질문 & 예시 & 실무 팁

| 항목 | 내용 |
|------|------|
| 정의 | 시스템과 데이터를 보호하기 위해 권한을 제한하고, 암호화하고, 감시하는 체계를 갖추는 설계 전략. 클라우드 보안 책임 공유 모델을 이해하고, 지속적인 보안 강화를 목표로 함 |
| 핵심 질문 | 누가 어떤 리소스에 접근할 수 있는가? / 데이터는 저장 시와 전송 시 모두 암호화되고 있는가? / 보안 로그를 수집하고 분석하고 있는가? / 보안 사고에 대한 대응 계획이 준비되어 있는가? |
| 예시 | IAM 사용자 최소 권한 정책 적용 / S3, EBS, RDS 암호화 설정 (KMS 사용) / CloudTrail로 API 호출 기록 추적 / AWS Config로 규정 준수 상태 확인 |
| 실무 팁 | MFA 활성화로 루트 계정 보호, IAM Access Analyzer로 비정상 접근 탐지 / 보안 그룹과 네트워크 ACL을 조합해 레이어드 보안 구성 / AWS GuardDuty, WAF, Shield와 같은 보안 서비스 통합 활용 |

#### 신뢰성(Reliability) — 핵심 질문 & 예시 & 실무 팁

| 항목 | 내용 |
|------|------|
| 정의 | 장애나 오류가 발생해도 시스템이 빠르게 복구되고 정상 동작을 지속할 수 있도록 설계하는 것. 고가용성과 내결함성을 확보하는 것이 핵심 |
| 핵심 질문 | 시스템 장애 시 자동 복구가 가능한가? / 장애가 발생해도 전체 서비스가 중단되지 않는가? / 장애 테스트 및 시뮬레이션을 주기적으로 수행하고 있는가? / 리전 또는 가용영역(AZ) 장애에도 대응할 수 있는가? |
| 예시 | EC2 Auto Scaling으로 인스턴스 자동 복구 / Amazon RDS Multi-AZ 구성으로 DB 이중화 / S3 버킷에 버전 관리 및 복원 설정 / Route 53 헬스 체크로 장애 감지 후 트래픽 우회 |
| 실무 팁 | 다중 AZ, 다중 리전 배포 전략 수립 / 백업 및 복원 전략: AWS Backup 또는 RDS 스냅샷 활용 / 모든 구성 요소에 대해 장애 발생 시 대응 계획(Runbook) 문서화 |

#### 성능 효율성(Performance Efficiency) — 핵심 질문 & 예시 & 실무 팁

| 항목 | 내용 |
|------|------|
| 정의 | 변화하는 요구사항에 따라 적절한 컴퓨팅 자원을 효율적으로 선택하고 사용하여, 최적의 성능을 유지하도록 설계하는 것. 확장성과 기술 혁신을 적극 활용함 |
| 핵심 질문 | 현재 리소스가 과도하거나 부족하지 않은가? / 수요 증가 시 자동 확장 가능한 구조인가? / 최신 기술(AI/ML, 서버리스 등)을 활용하고 있는가? / 다양한 리전과 가용영역에서 성능이 일관되게 유지되는가? |
| 예시 | Auto Scaling으로 트래픽 증가 시 EC2 자동 확장 / Lambda 사용으로 짧은 요청에 빠르게 대응 / Amazon CloudFront로 정적 콘텐츠 캐싱 및 성능 개선 |
| 실무 팁 | 워크로드 특성에 맞춰 적절한 인스턴스 타입 선택(예: CPU/GPU 최적화) / 성능 모니터링(CloudWatch)으로 병목 구간 확인 및 개선 / Amazon Compute Optimizer를 활용해 권장 인스턴스 제안 받기 / 서버리스, 컨테이너 등 최신 기술 적용 검토로 아키텍처 현대화 추진 |

#### 비용 최적화(Cost Optimization) — 핵심 질문 & 예시 & 실무 팁

| 항목 | 내용 |
|------|------|
| 정의 | 비즈니스 목표를 달성하기 위해 필요한 리소스를 적절한 크기로 선택하고, 낭비 없이 비용을 효율적으로 사용하는 설계 전략을 의미. 사용량 기반 과금 모델을 이해하고 통제하는 것이 핵심 |
| 핵심 질문 | 불필요하게 사용 중인 리소스는 없는가? / 더 저렴한 서비스 옵션(예: 스팟 인스턴스, 서버리스)이 있는가? / 정기적으로 비용을 분석하고 있는가? / 리소스의 수요에 맞게 자동으로 확장/축소되고 있는가? |
| 예시 | 미사용 EC2, EBS 정리 / EC2 예약 인스턴스 또는 Savings Plans 적용 / Amazon S3의 수명 주기 정책 설정으로 저장 비용 절감 |
| 실무 팁 | Cost Explorer와 AWS Budgets로 비용 시각화 및 경고 설정 / 스케줄링 태그를 설정해 업무 시간 외 EC2 인스턴스 자동 종료 / 비용 분석 보고서를 정기적으로 팀과 공유하여 책임 분산 |

#### 지속 가능성(Sustainability) — 핵심 질문 & 예시 & 실무 팁

| 항목 | 내용 |
|------|------|
| 예시 | 서버리스(Lambda 등)로 컴퓨팅 낭비 최소화 / 오토스케일링, 수요 기반 인프라 구성 / 데이터 압축 및 스토리지 수명 주기 정책(S3 Lifecycle Policy) 활용 |
| 실무 팁 | S3에 저장된 데이터를 수명 주기 정책으로 관리 / 워크로드 사용률을 시각화하고 과도한 리소스 제거 / 가능한 경우 서버리스로 전환하여 항상 켜져 있는 인프라 제거 |

## 8. AWS Well-Architected Framework Tool

### 8.1 Well-Architected Framework Tool이란?

**AWS Well-Architected Framework Tool**은 Well-Architected Framework의 원칙에 맞게 설계되었는지 **점검하고 개선 가이드를 제공하는 평가 도구**다.

- **질문 기반 진단 → 자동 위험 분석 및 모범 사례 제안**
- AWS 콘솔에서 **무료로 제공**

### 8.2 Well-Architected Framework Tool 장점

- AWS Well-Architected Tool은 클라우드 아키텍처 품질 점검의 **필수 도구**
- 설계 개선의 출발점이자, 조직 내 보안 및 운영 품질 향상 도구
- **자동화된 질문 기반 리뷰**로 위험 요소를 쉽게 식별 가능
- 신규 서비스 설계, 기존 시스템 진단, 개선 우선순위 정리에 유용

### 8.3 Well-Architected Tool 활용 방법

1. AWS 콘솔에서 Well-Architected Tool 접속
2. 워크로드(Workload) 생성 및 정보 입력
3. 6개 Pillar별 질문에 답변 (예: "모든 API 호출이 기록되고 있는가?")
4. 도구가 자동으로 High Risk / Medium Risk 항목 분류
5. 개선 계획(Improvement Plan) 생성 및 우선순위에 따라 조치
